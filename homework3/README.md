# Домашняя работа №3: JSP-фронтенд для Маркетплейса

В прошлой работе вы построили HTTP API маркетплейса, которое отвечало клиентам «голым» текстом. Теперь наша задача — обрасти пользовательским интерфейсом. Вы должны подключить представления на JSP к тем же самым ручкам (эндпоинтам), которые вы уже реализовали в [homework2](../homework2/README.md), и при этом освоить четыре ключевых механизма веб-слоя: **JSP-скриптлеты**, **JSTL**, **JavaScript** на клиенте, а также серверные **redirect** и **forward** и работу с **HTTP-сессией**.

## Архитектура: Servlet + JSP (MVC Model 2)

### Конфигурация сервлетов через web.xml

В этой работе **запрещается** использовать аннотацию ``` @WebServlet ``` — все сервлеты должны быть зарегистрированы вручную в дескрипторе развёртывания ``` src/main/webapp/WEB-INF/web.xml ```. Для каждого сервлета пропишите пару ``` <servlet> ``` (имя и полное имя класса) и ``` <servlet-mapping> ``` (путь из прошлого ДЗ). Пример:

```xml
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee
                             https://jakarta.ee/xml/ns/jakartaee/web-app_6_0.xsd"
         version="6.0">

    <servlet>
        <servlet-name>productServlet</servlet-name>
        <servlet-class>ru.itis.java_505_2627.ProductServlet</servlet-class>
    </servlet>
    <servlet-mapping>
        <servlet-name>productServlet</servlet-name>
        <url-pattern>/api/products</url-pattern>
    </servlet-mapping>

</web-app>
```

Зарегистрируйте так все сервлеты: ``` ProductServlet ```, ``` UserServlet ```, ``` CartServlet ```, ``` OrderServlet ```, ``` ReviewServlet ```, ``` AdminStatServlet ``` и новый ``` LoginServlet ```. Обратите внимание: если в web.xml объявлен дескриптор (с корневым элементом ``` web-app ```), аннотации на этих классах игнорировать/убирать нужно аккуратно — за двойную регистрацию (аннотация + маппинг в web.xml с тем же URL) контейнер может пожаловаться при старте.

Сохраняйте архитектуру прошлой работы: данные по-прежнему живут в мок-хранилищах внутри сервисов (``` ProductService ```, ``` UserService ``` и т.д.), бизнес-логика не должна появляться ни в сервлетах, ни тем более в JSP. Теперь разделение ответственности становится таким:

* **Сервлеты (контроллеры)** — принимают запрос, работают с сессией, вызывают сервисы, кладут данные в атрибуты запроса (``` req.setAttribute(...) ```), после чего **форвардят** запрос на JSP-страницу через ``` req.getRequestDispatcher("/WEB-INF/jsp/...").forward(req, resp) ```.
* **JSP (представления)** — только рисуют HTML из атрибутов запроса. Никакого обращения к сервисам и мок-хранилищам из JSP быть не должно.
* **Редиректы** — после изменений данных (POST/PUT/PATCH/DELETE) контроллер не должен рендерить страницу сам: выполняйте ``` resp.sendRedirect(...) ``` на GET-страницу (паттерн Post/Redirect/Get), чтобы обновление страницы в браузере не повторяло мутацию повторно.

Все JSP-файлы складывайте в ``` src/main/webapp/WEB-INF/jsp/ ```. Файлы внутри ``` WEB-INF ``` недоступны клиенту напрямую — пользователь сможет увидеть страницу только через сервлет, что и нам нужно.

### Зависимости (JSTL)

Для работы с JSTL добавьте в ``` pom.xml ``` зависимость:

```xml
<dependency>
    <groupId>org.glassfish.web</groupId>
    <artifactId>jakarta.servlet.jsp.jstl</artifactId>
    <version>3.0.1</version>
</dependency>
<dependency>
    <groupId>jakarta.servlet.jsp.jstl</groupId>
    <artifactId>jakarta.servlet.jsp.jstl-api</artifactId>
    <version>3.0.0</version>
</dependency>
```

Обратите внимание: старые туториалы из интернета используют ``` javax.servlet ``` и тегlib с URI ``` http://java.sun.com/jsp/jstl/core ```. У вас Jakarta EE — правильный URI: ``` jakarta.tags.core ```.

## Требования к технологиям (матрица покрытия)

Каждая ручка получает HTML-интерфейс, и вы обязаны продемонстрировать владение всеми четырьмя технологиями. Итоговое покрытие должно выглядеть так:

| Ручка | Страница JSP | Технологии во view |
|---|---|---|
| ``` /api/products ``` | ``` products.jsp ``` | Чистый JSP (скриптлеты и выражения) |
| ``` /api/users ``` | ``` user-profile.jsp ``` | JSTL (теги ``` <c:if ```, ``` <c:choose ```, ``` <c:forEach ```) |
| ``` /api/cart ``` | ``` cart.jsp ``` | JSTL + JavaScript (fetch/AJAX, живое обновление корзины) |
| ``` /api/orders ``` | ``` orders.jsp ``` | Чистый JSP + JavaScript |
| ``` /api/reviews ``` | ``` reviews.jsp ``` | JSTL + JSP-скриптлеты вместе |
| ``` /api/admin/stats ``` | ``` admin-stats.jsp ``` | JSTL + JavaScript + защита через сессию |

## Детальные требования по страницам

### 1. Каталог товаров — ``` ProductServlet ``` (``` /api/products ```)

Страница ``` products.jsp ``` должна быть написана на **чистом JSP**, без JSTL. Используйте скриптлеты (``` <% ... %> ```), выражения (``` <%= ... %> ```) и declaration (``` <%! ... %> ```): например, выведите список товаров циклом ``` for ``` прямо в скриптлете, пронумеруйте позиции. На странице должна быть HTML-форма добавления товара (метод POST), которая отправляется на тот же URL ``` /api/products ```. Сервлет обрабатывает POST, добавляет товар в мок-хранилище и делает **редирект** обратно на GET-страницу каталога. Также оставьте прежнее текстовое поведение для cURL-клиентов: если запрос пришёл с заголовком ``` Accept: text/plain ``` или без него, отдавайте текст, как в homework2; если ``` Accept: text/html ``` (браузер) — форвард на JSP.

### 2. Профиль покупателя — ``` UserServlet ``` (``` /api/users ```)

Страница ``` user-profile.jsp ``` должна быть построена **только на JSTL**: никакого Java-кода в скриптлетах. Выведите карточку пользователя: имя, email, статус. Статус подсветите через ``` <c:choose ```: "active" — зелёным, "blocked" — красным. Ниже разместите две формы: полное обновление профиля (PUT эмулируйте скрытым полем или параметром ``` _method=PUT ``` с разбором его в сервлете) и частичное обновление статуса (PATCH, аналогично). После каждой мутации — **редирект** на страницу профиля. Если пользователь с указанным ``` id ``` не найден, форвардните на страницу ошибки ``` /WEB-INF/jsp/error.jsp ``` с кодом ``` 404 ```, передав сообщение об ошибке через атрибут запроса.

### 3. Корзина — ``` CartServlet ``` (``` /api/cart ```)

Страница ``` cart.jsp ``` — витрина комбинации **JSTL + JavaScript**. Начальный список товаров корзины отрендерите тегом ``` <c:forEach ``` по атрибуту запроса, но добавление и удаление товаров должно происходить **без перезагрузки страницы**: напишите на чистом JavaScript (или fetch) код, который отправляет POST/DELETE на ``` /api/cart ``` и по ответу обновляет DOM. Сервлет, обнаружив AJAX-запрос (например, заголовок ``` X-Requested-With: XMLHttpRequest ```), отвечает JSON-ом со свежим содержимым корзины, а обычный браузерный запрос — форвардом на ``` cart.jsp ```.

### 4. Заказы — ``` OrderServlet ``` (``` /api/orders ```)

Страница ``` orders.jsp ``` — **чистый JSP + JavaScript**. Список заказов отрендерите скриптлетами, а кнопкой «Оформить заказ» повесьте JavaScript-обработчик, который отправляет POST на ``` /api/orders ``` и показывает пользователю всплывающее уведомление (alert или собственный баннер) с номером созданного заказа. После оформления заказа через обычную форму (без JS) сервлет кладёт созданный заказ в **сессию** (см. раздел про сессии) и делает редирект на страницу истории заказов.

### 5. Отзывы — ``` ReviewServlet ``` (``` /api/reviews ```)

Страница ``` reviews.jsp ``` должна сочетать **JSTL и скриптлеты одновременно**: список отзывов выведите через ``` <c:forEach ```, а блок с условной логикой (например, счётчик отзывов и «плашку» модератора) — скриптлетами и выражениями. Форма добавления отзыва отправляет POST с текстом и ID товара; после сохранения — редирект на эту же страницу с якорем к новому отзыву. Кнопка удаления отзыва (DELETE) доступна только «модератору»: признак модератора должен храниться в **сессии**, и если его там нет, сервлет редиректит на страницу входа модератора или отдаёт ``` 403 ```.

### 6. Админ-статистика — ``` AdminStatServlet ``` (``` /api/admin/stats ```)

Полностью переделайте авторизацию с прошлого ДЗ: вместо заголовка ``` Admin-Token ``` используйте **сессию**. Заведите страницу логина ``` /login ``` (сервлет ``` LoginServlet ``` + ``` /WEB-INF/jsp/login.jsp ```): форма принимает логин и пароль (секреты задайте константами в сервисе), при успехе пишет в сессию атрибут, например ``` session.setAttribute("admin", true) ```, и редиректит на статистику; при неудаче — форвард обратно на ``` login.jsp ``` с сообщением об ошибке. ``` AdminStatServlet ``` проверяет атрибут сессии: если админ не залогинен — **редирект** на ``` /login ```, если залогинен — форвард на ``` admin-stats.jsp ```, где JSTL выводит счётчики, а JavaScript периодически (раз в N секунд) опрашивает ``` GET /api/admin/stats ``` и обновляет цифры на лету. Добавьте на страницу кнопку «Выйти» (``` /logout ```), которая инвалидирует сессию (``` session.invalidate() ```) и редиректит на логин.

## Работа с сессией — обязательные требования

Сессия должна использоваться осмысленно как минимум в трёх местах:

1. **Корзина покупателя** — содержимое корзины храните в атрибуте сессии, а не в общей статической коллекции: у каждого посетителя своя корзина (это естественная замена мок-хранилищу для ``` CartServlet ```).
2. **Флеш-сообщения** — после редиректа положите короткое сообщение («Товар добавлен», «Профиль обновлён») в атрибут сессии, JSP его прочитает, покажет баннером и сразу удалит из сессии (flash-паттерн).
3. **Авторизация администратора** — как описано выше, признак залогиненного админа живёт в сессии.

Проследите, чтобы при первом обращении к любым страницам сессия создавалась корректно, а если вы кладёте в сессию объекты сервисов — не допускайте утечек памяти.

## Redirect и Forward — обязательные требования

Вы обязаны использовать оба механизма, и вы должны понимать разницу:

* **Forward** (``` RequestDispatcher.forward ```) — внутреннее серверное перенаправление, браузер о нём не знает, URL не меняется. Используйте его для перехода «контроллер → JSP» при рендеринге страниц.
* **Redirect** (``` resp.sendRedirect ```) — ответ с кодом ``` 3xx ``` и заголовком ``` Location ```, браузер делает новый запрос. Используйте его после всех мутаций (POST/PUT/PATCH/DELETE) и при доступе к закрытым страницам без авторизации.

В комментарии или в отчёте укажите, где какой механизм применён и почему.

## Как проверять

Приложите к работе скриншоты каждой страницы в браузере **и** подготовьте файл с cURL-командами, демонстрирующими, что текстовое поведение API из homework2 не сломалось:

```bash
  # Текстовая версия каталога (API-клиент)
  curl -X GET http://localhost:8080/api/products

  # HTML-версия каталога (браузер)
  curl -X GET -H "Accept: text/html" http://localhost:8080/api/products

  # Добавление товара через форму с последующим редиректом
  curl -X POST -d "name=MacBook Pro" http://localhost:8080/api/products -i

  # Логин администратора (создаёт сессию, смотрите заголовок Set-Cookie)
  curl -X POST -d "login=admin" -d "password=secret" http://localhost:8080/login -i -c cookies.txt

  # Статистика с сессией (куки из cookies.txt)
  curl -X GET http://localhost:8080/api/admin/stats -b cookies.txt -i
```

Проверьте по логам (SLF4J остаётся обязательным), что на каждый запрос пишется метод, путь, наличие/отсутствие сессии и тип ответа (forward или redirect).
